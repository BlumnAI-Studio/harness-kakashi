# 영입 워크플로우 (Recruit Workflow)

> 정원의 꽃은 배달되지 않는다 — 당신의 토양에서 피운다.

하네스는 전문가 에이전트를 **미리 담아 배포하지 않는다**.
대신 이 워크플로우로 **당신의 프로젝트에 맞는 전문가를 직접 영입**한다.
영입은 언제나 사용자의 선택이다. 쓰지 않을 전문가를 처음부터 모두 심으면 혼선만 생긴다 —
**작게 시작해서, 필요할 때 하나씩** 심는 것이 원칙이다.

---

## 1. 에이전트 타입 — 세 종류의 주민

| 타입 | 은유 | 가진 것 | 역할 | 예 |
|------|------|--------|------|-----|
| `specialist` | 꽃 | 도구·도메인 지식 | 코드/산출물을 점검·개선 | 성능 정찰꾼, 테스트 파수꾼, 보안 경비 |
| `sage` | 소환된 현자 | 사상(思想) | 작업 방식 자체를 평가 (방법론) | 데밍(PDSA), 에반스(DDD) |
| `keeper` | 지기(番) | 구조·자산 관리 책무 | 하네스의 문서/뷰/그래프 등 자산을 지킴 | 별지기(위키링크), 지도지기(뷰 동기화) |

- `tamer`(정원지기)는 유일한 기본 내장 메타 에이전트로, 타입 분류 밖이다.
- 처음에는 대부분 `specialist`만 필요하다. `sage`/`keeper`는 하네스가 성숙한 뒤 고려한다.

---

## 2. 영입 원천 (Source)

전문가는 무(無)에서 만들지 않는다. 검증된 원천에서 증류한다:

1. **외부 스킬/레포** — 잘 만든 오픈소스 스킬 저장소를 분석해 설계 원칙을 차용 (사륜안)
2. **방법론/인물** — 검증된 거장의 사상을 정전(canon)으로 정리해 sage로 영입
3. **프로젝트 자체** — 반복되는 점검 패턴을 관찰해 specialist로 승격
4. **영입 카탈로그** — 마더 정원에서 실전 검증된 전문가 명부: [recruit-catalog.md](recruit-catalog.md)

---

## 3. 영입 절차 — 5-파일 패턴

영입 1건은 최대 5개 파일을 만들거나 갱신한다. (†는 선택)

| # | 파일 | 내용 | 필수 |
|---|------|------|------|
| 1 | `harness/agents/{name}.md` | 에이전트 정의 (아래 스켈레톤) | ✅ |
| 2 | `harness/knowledge/methodology/{doctrine}.md` | 사상 정전 — sage 영입 시. 1차 출처 인용 필수 | † sage만 |
| 3 | `harness/knowledge/{topic}.md` | 도메인 지식/운용 문서 — 원천 분석 결과 | † 권장 |
| 4 | `harness/harness.config.json` | `agents` 배열에 추가 (+타입별 확장 필드) | ✅ |
| 5 | `harness/docs/vX.Y.Z.md` | 영입 기록 (Minor 버전 bump) | ✅ |

**절차:**
1. **원천 분석** — 영입 원천(레포/방법론/패턴)을 읽고 핵심 원칙 3~5개를 추출
2. **타입 판정** — specialist / sage / keeper 중 판정 (§1 표 기준)
3. **파일 생성** — 위 5-파일 패턴대로 생성 (사용자 승인 후)
4. **검증** — Mode E(구조 검증)로 config ↔ 파일 정합, 트리거 중복 확인

## 4. 에이전트 정의 스켈레톤

```markdown
---
name: {에이전트명}
type: {specialist | sage | keeper}
persona: {페르소나 이름} (선택)
triggers:
  - "{트리거 문구 1}"
  - "{트리거 문구 2}"
description: {한 줄 설명}
---

# {에이전트 이름}

## 역할
{무엇을 하는 에이전트인지, 무엇을 하지 않는지}

## 점검 절차
### Step 1: ...
### Step 2: ...

## 심각도 분류
| 등급 | 기준 |
|------|------|
| Critical | ... |
| Moderate | ... |
| Info | ... |

## 평가축 (선택 — 이 에이전트 고유의 축이 필요할 때만)
| 축 | 평가 대상 | 등급 |
|----|----------|------|

## 경계
- **하는 것**: ...
- **하지 않는 것**: ...
```

> 평가축은 **필요할 때만** 정의한다. 축이 없으면 하네스 기본 평가(evaluation.md)를 따른다.
> 에이전트마다 축을 만들면 평가 체계가 난립한다 — [references/evaluation.md](evaluation.md)의 통합 원칙 참조.

## 5. 엔진(워크플로우) 스켈레톤

여러 에이전트를 조합해 실행할 때만 엔진을 만든다:

```markdown
---
name: {엔진명}
triggers:
  - "{트리거 문구}"
description: {한 줄 설명}
agents:
  - {참여 에이전트 1}
  - {참여 에이전트 2}
---

# {엔진 이름}

## 실행 순서
1. {에이전트1} — {수행 내용}
2. {에이전트2} — {수행 내용}

## 병렬 실행 가능 구간
- [{에이전트1}, {에이전트2}] — 동시 실행 가능

## 결과 집계
{개별 결과를 어떻게 종합할지 — 합성 등급을 만들려면 규칙을 여기 명시}
```

## 6. config 확장 필드 (타입별)

에이전트 타입에 따라 `harness.config.json`에 선택적으로 추가하는 필드:

- `evaluation` — sage를 기본 평가자로 상시 부착할 때 (`base.agent`, `alwaysOn`, `appliesTo`)
- `keepers` — keeper의 감시 범위/트리거 (`scope`, `exclude`, `trigger`, `alwaysOn`)
- `design` — 디자인 정전을 운용할 때 (`principle`, `owner`, `files`)

스키마 상세: SKILL.md의 "하네스 초기화" 섹션 참조.
이 필드들은 **전부 선택**이다 — 해당 타입을 영입하기 전에는 추가하지 않는다.

---

## 7. 안티패턴

- ❌ 검증되지 않은 원천에서 즉흥 영입 — 원천 분석 없이 만든 에이전트는 점검 기준이 없다
- ❌ 한 번에 5명 이상 영입 — 쓰지 않는 전문가는 혼선이다. 필요해질 때 심는다
- ❌ 영입마다 전용 평가축 신설 — 기본 평가로 충분하지 않을 때만 축을 만든다
- ❌ 트리거에 프로젝트 고유 문구를 표준 스킬에 등록 — [references/skill-separation.md](skill-separation.md) 준수
